# I2P SUPPORT IN DEFICHAIN

DeFiChain can connect to peers over I2P through a [SAM v3.1](https://i2p.net/en/docs/api/samv3)
bridge ("SAM proxy"). The bridge translates the I2P tunnels into a TCP stream
that the node speaks the normal P2P protocol over.

The implementation follows upstream Bitcoin Core (the I2P SAM transport that was
added in Bitcoin Core v22.0) and is limited to the transport: the
representation of the I2P destinations (`.b32.i2p` addresses, the `NET_I2P`
network type) was added separately and the addresses are neither persisted in
the address manager nor relayed to the other peers.

## 1. Run a SAM bridge

The node does not implement the I2P protocol itself, it needs a bridge that
speaks the SAM v3.1 protocol. Both `i2pd` and the Java I2P router provide
such a bridge:

    i2pd --sam.enabled=true --sam.bind=127.0.0.1:7656

The bridge listens on the TCP port 7656 by default.

## 2. Connect to an I2P peer

    -i2psam=<host:port>   Use the SAM bridge at <host:port> (default port: 7656)
    -i2p=<host:port>      Alias of -i2psam

The bridge is **not** a SOCKS5 proxy: it is not registered with `-proxy` and it
is not used for the `.onion` addresses. The option only selects the bridge for
the I2P transport.

An invalid value is a startup error, an unreachable bridge is not: the session
is created lazily (on the first I2P connection attempt) and it is re-created
after a failure, so the node stays alive and keeps retrying.

The peers are then configured like any other peer, with their `.b32.i2p`
address:

    defid -i2psam=127.0.0.1:7656 -connect=<destination>.b32.i2p

I2P destinations are portless (the SAM v3.1 protocol has no notion of a
destination port). A port in the configuration string is accepted but ignored,
the node always uses the port 0 for the I2P peers.

## 3. Accept inbound I2P connections

    -i2pacceptincoming    Accept inbound I2P connections through the bridge

The option is disabled by default: an always-on inbound I2P listener is an
operator-visible change of the attack surface. The option requires
`-i2psam` to be set, and `-listen=0` implies `-i2pacceptincoming=0`.

The inbound connections go through the regular peer handling: they are
subject to the same connection limits (`-maxconnections`) and to the same
message handling as the inbound TCP connections.

An inbound I2P peer **cannot be banned**: the ban list (`-banlist`, the
`setban` RPC) is based on the legacy (pre-BIP155) address representation and
it has no representation for the I2P destinations, so an I2P address is
rejected by the ban list. Covering the I2P destinations with the ban list
would require a representation for `NET_I2P` in the subnet code and is out of
the scope of the I2P transport. Use the connection limits (and the other
transport level controls) to limit the inbound I2P peers.

## 4. The private key

The node needs an I2P destination to be reachable. The destination (the
private key) is generated by the bridge on the first start and stored in

    <datadir>/i2p_private_key

The file is written with the permissions 0600 and it is never logged (neither
is the `SESSION CREATE` request that contains the key). A missing or corrupt
file is regenerated, so the file can be deleted without breaking the node
(the node then simply gets a new destination).

## 5. Logging

The I2P transport has its own log category:

    -debug=i2p

The category reports the creation and the destruction of the SAM sessions, the
own I2P address and the errors of the connection attempts. The private key and
the destination of the session are never logged.

## 6. Trust model

The SAM bridge sees the whole traffic: it can read and modify it and it holds
the private key of the node. The bridge therefore has to be trusted to the
same degree as a SOCKS5 proxy. Do not expose the SAM port of the bridge to
the network.

The I2P addresses of the peers are neither stored in `peers.dat` nor
advertised to the other peers: the I2P peers have to be configured locally.
